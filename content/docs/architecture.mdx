# Architecture map (home-ai)

Factual map of where things live. Read this before exploring `src/` — it should
save you most of the grep work. Step-by-step flows are in `/docs/flows`.

> Keep this file in sync when you move/rename/add modules or tables
> (see "Keeping docs current" in AGENTS.md).

## Folder layout

| Folder | Purpose |
|---|---|
| `src/app/` | Next.js App Router: pages + API routes |
| `src/app/(app)/settings/` | Settings: **one route segment per tab** (`general`, `intelligence`, `memory`, `access`, `mcp`, `usage`). `layout.tsx` carries the header + nav, `page.tsx` redirects to `general`. Each tab only loads its own data; shared state and types in `src/components/settings/shared.ts` (`useSettings`, `useAction`, `useSyncFrom`, `putSettings`) |
| `src/app/a/[slug]/` | Serves a generated app inside its sandboxed iframe page |
| `src/app/d/[slug]/` | Serves a dashboard with 12-col grid of live app iframes |
| `src/app/api/` | REST routes (`auth`, `apps`, `connections`, `scripts`, `settings`, `dashboards`, `tokens`, `templates`, `assistant`) + public incoming webhooks (`hooks`) + MCP endpoint (`mcp`: `POST /` Streamable HTTP + `GET /tools` catalog + `GET /calls` history) |
| `src/app/assistant/` | Global assistant — dedicated full-screen UI `assistant/[[...threadId]]` (catch-all: `/assistant` = new conversation, `/assistant/<id>` = existing thread) + API (`assistant`, `assistant/threads`) |
| `src/components/` | React UI; primitives in `src/components/ui`, global entrypoints `CommandPalette.tsx` (⌘K) + `agent/Overlay.tsx` (⌘J) + `agent/AgentContext.tsx` (scope) mounted in `AppShell`, `agent/*` (chat, sidebar, parts) + `chat/Markdown.tsx` |
| `src/components/agent/` | Assistant UI: `ChatView.tsx` (`useChat` + rendering per part type), `ThreadSidebar.tsx` (presentational, list provided by the server), `Overlay.tsx` (contextual drawer, ⌘J), `AgentContext.tsx` (scope + opening), `parts/` (Reasoning, Tool, PlanCard) |
| `src/components/scripts/` | Pieces extracted from `ScriptsManager`: `types.ts` (shared types + `RUN_VARIANT`), `SchedulePreview.tsx`, `RunRow.tsx` |
| `src/components/settings/` | `shared.ts`: types for `/api/settings` + `useSettings`/`useAction`/`useSyncFrom`/`putSettings`, shared by the tabs |
| `src/db/` | Drizzle schema, client, migration runner |
| `src/lib/` | Framework-agnostic helpers (runtime bridge, auth config, errors, crypto, env) + the HTTP boundary: `route.ts` (API routes) and `api-client.ts`/`use-resource.ts` (React side) |
| `src/services/` | Business logic grouped by domain folders (`apps/`, `agent/`, `browser/`, `scripts/`, `connections/`, `generation/`, `llm/`, `storage/`, `templates/`, `user-state/`) — API routes stay thin and delegate here |
| `templates/` | Prebuilt app templates: `templates/<slug>/{template.json, app.html}` — `todo`, `budget` (Chart.js), `planning`, `notes` — installed on demand via `installTemplate` |
| `drizzle/` | Generated SQL migrations |

## Services (`src/services/`, grouped by domain)

### `apps/`

| File | Purpose |
|---|---|
| `apps.ts` | App CRUD, slugs (`slugify`), `getAppOwnerId`, `AppError` |
| `versions.ts` | `createVersion`, `listVersions`, `getVersion`, `rollbackToVersion`, `currentHtml` |
| `manifest.ts` | Exposure manifest: zod schema (`appManifestSchema`), extraction from HTML (`extractManifestFromHtml`), execution of declared tools (`executeManifestTool`: get/set/list/append/remove/toggle/update) + JSON Schema → zod conversion (`jsonSchemaToZod`) |

### `tools/`

Shared tool registry: **one definition per tool**, consumed by both
surfaces (assistant + MCP). Before this, the 18 common tools were written twice,
with separate schemas and handlers that had drifted apart.

| File | Purpose |
|---|---|
| `define.ts` | `defineTool({ name, title, description, input, exposure, destructive, handler })` → `ToolDef`. The handler receives **already validated and typed** arguments (`z.infer`), which is why the defensive `String(x)` calls are gone. `run()` is async: a validation failure gives a rejected promise |
| `registry.ts` | `toolRegistry`: concatenates the `tools.ts` of each domain. Adding a tool = writing it in its domain + one line here |
| `registry.test.ts` | Guardrails: no duplicate names, names accepted by MCP, non-empty description, schema is indeed a `z.object` (the MCP adapter reads `.shape`), effective validation |

Definitions live next to their service: `apps/tools.ts`, `scripts/tools.ts`,
`dashboards/tools.ts`, `storage/tools.ts`, `connections/tools.ts`,
`templates/tools.ts`, `agent/own-tools.ts`. Same principle as
`connections/registry.ts`. By default a tool is exposed on **both**
surfaces (`exposure` lets you restrict that).

### `storage/`

Unified KV storage: **a single implementation** for all three scopes
(app, global, script). Before this, three near-identical modules (~520 lines) had
already drifted apart — `script_storage` had neither `kind` nor `schema`.

| File | Purpose |
|---|---|
| `scope.ts` | `StorageScope` (`app`/`global`/`script`) + `appScope`/`globalScope`/`scriptScope` constructors, and a `ScopeRepo` per scope: target table, read resolution (global: its own key then falls back to a `family` key), list filter, presence of `visibility`. Deliberately dumb — no business logic |
| `storage.ts` | All the logic, written once: `storageGet/GetMeta/Set/List/Delete/Clear/RowOp`, JSON round-trip, `baseUpdatedAt` conflict guard (409 at second-level granularity), atomic row operations in a transaction (`applyRowOp`), `isJsonSerializable` |

The three tables stay separate: `app_storage.app_id` and `script_storage.script_id`
carry an `ON DELETE CASCADE` that a single shared table couldn't reproduce
(one FK can't target three parents).

### `messages/`

| File | Purpose |
|---|---|
| `chat.ts` | Generation chat (apps/scripts): `addGenerationMessage` / `listGenerationMessages` / `listAppMessages` / `listScriptMessages`, built on top of `assistant_threads`/`assistant_messages` (contextKind `app`/`script`) |
| `threads.ts` | Storage for that chat (`getOrCreateThread`, `addMessage`, `listMessages`). Flat role/content schema, independent from the assistant's `agent_*` tables |

### `scripts/`

A server script (public concept: "script") is an `async function main(home)` executed in `node:vm`,
triggered by a **trigger**: `schedule` (5-field cron expression, default), `manual` (on demand) or
`webhook` (public POST `/api/hooks/<slug>` + secret, payload exposed via `home.webhook.payload`).

| File | Purpose |
|---|---|
| `scripts.ts` | Script CRUD, versions (`snapshotScriptVersion`), `computeNextRun`/`nextRunOrNull` (empty schedule = unscheduled), `isScheduled`/`generateWebhookSlug`/`generateWebhookSecret`, `getScriptByWebhookSlug` (public route), ACL (`canReadScript`/`canWriteScript`), `ScriptError` |
| `runner.ts` | Execution in `node:vm`: `runScript(scriptId, {payload})`, `runDueScripts` (only picks up `triggerKind = 'schedule'`), `listScriptRuns` |
| `sdk.ts` | `buildScriptSdk(ownerId, {scriptId, runId, webhookPayload})` — server-side twin of the iframe `homeSDK`; `home.storage.*` is always on `scriptScope`, `home.app(appId).storage.*` gives access to an app's storage (access check on every call). Exposes `home.webhook.payload` (null outside a webhook run) |
| `traced-sdk.ts` | Tracing proxy (`createTracedHome`) — every `home.*` call becomes a span, `home.step`/`// @step` pragmas produce `step` spans |

### `browser/`

| File | Purpose |
|---|---|
| `cdp.ts` | Minimal CDP client over a native WebSocket and page wrapper |
| `lightpanda.ts` | Health check and startup of the local Lightpanda sidecar |
| `sessions.ts` | Script browser sessions, actions, TTL and per-run cleanup |

### `connections/`

| File | Purpose |
|---|---|
| `connections.ts` | External connections CRUD, secrets encrypted at rest; `getConnectionConfigByType`, `ConnectionError` — **delegates to the registry** (`getProvider().schema/test/resolve`) |
| `definition.ts` | `ConnectionProvider<TConfig>` contract (zod schema + test + sdk namespace/methods) |
| `registry.ts` | Central registry: `connectionRegistry` + `methodRegistry` (`fullMethod` → provider). Adding a connection = 1 provider file + 1 line in the registry. Also generates `getSdkPromptLines()` for the LLM |
| `google.ts` | OAuth 2.0 + Drive/Calendar/Gmail/Sheets — exports `googleProvider` (resolve = refresh). Contracts normalized on the service side so generated apps have nothing to work around: `drive.read` always returns `content` as a string or `null` (googleapis parses a JSON body into an object) and exports native Google files in whatever format they accept (Sheets → CSV, Docs/Slides → text); `drive.list` accepts `orderBy`/`pageSize`; `sheets.read` flags `truncated` when the default range cuts data off; `sheets.update` writes to a precise range. A `note` field explains any limitation (CSV first sheet only, PDF not extractable) |
| `email.ts` | SMTP/IMAP — exports `smtpProvider` + `imapProvider` (shared `mail` namespace) |
| `telegram.ts` | Telegram Bot API — exports `telegramProvider` |
| `notion.ts` | Notion API — exports `notionProvider` |
| `homeassistant.ts` | Home Assistant REST — exports `homeassistantProvider` (namespace `homeassistant`, no more `hass`) |
| `weather.ts` | OpenWeatherMap — exports `weatherProvider` |
| `webhook.ts` | Generic webhook + `httpFetch` (SSRF-guarded, **outside the registry** for `http.fetch`) — exports `webhookProvider` |

### `generation/`

| File | Purpose |
|---|---|
| `app.ts` | App generation: `planApp`, `codeApp`, `extractHtml`, `looksTruncatedHtml`, `containsForbiddenStorage`/`fixForbiddenStorage` (anti-localStorage) + `containsForbiddenAlpine`/`fixForbiddenAlpine` (anti-Alpine.data), Chart.js among the preloaded libs, the CODER/PLANNER prompts. Automatic **iteration mode** as soon as a current HTML exists: planner returns `{changes,keep,risks}`, coder does a **targeted PATCH** with history (`formatHistory`) + truncated HTML (`truncateHtml`) |
| `script.ts` | Script generation: `generateScript` (single pass, assistant/MCP) + **two phases** `planScript`/`codeScript` (+ streams, PLANNER/CODER prompts, `parseGeneratedScript`) for the UI |
| `shared.ts` | `chatWithTruncationRetry` (retry with doubled budget), `GenerateOptions`, `languageInstruction`, `formatHistory`, `truncateHtml`, `extractStorageKeys` |

### `llm/`

| File | Purpose |
|---|---|
| `llm.ts` | OpenAI-compatible client, multi-provider; encrypted key resolution (`resolveApiKey`), `LlmError`, `chatCompletion`/`chatCompletionDetailed`/`chatCompletionStream`, `sanitizeChatMessages`. Tool calling no longer lives here: the assistant goes through `services/agent/` (AI SDK) |
| `ai-sdk.ts` | AI SDK factory: `getAiModel(provider, modelId)` via `createOpenAICompatible` with `baseURL` and `apiKey: () => resolveApiKey(provider)` (encrypted DB key wins over env). Used by the new UIMessage assistant flow |
| `settings.ts` | Per-user model/provider settings; `getEffectiveDefaults` |

### `user-state/`

| File | Purpose |
|---|---|
| `types.ts` | `UserStateGraph` contract: nodes (`user`/`connection`/`app`/`script`/`storage`/`memory`/`thread`/`signal`) + edges (`OWNS`/`ATTACHED_TO`/`STORES`/`RELATES_TO`/`ROUTINE`/`HEALTH`/`INTEREST`/`ACTIVITY`), weights 0..1 |
| `graph.ts` | `getUserStateGraph(userId)` — **derived view** (never written) built on demand: the user's apps/scripts/connections/memory/storage/threads + derived signals. Routines via `describeSchedule` (readable label for a 5-field cron expression), memory→app/storage links by keyword (`matchMemoryToApps`/`matchMemoryToStorages`), health (failing scripts, inactive connections), interests (≥2 memories linked to one app) |
| `schedule.ts` | `describeSchedule` — best-effort translation of a schedule expression into a label (e.g. "Every Monday at 9:00 AM"). Pure, testable without a DB |
| `match.ts` | Memory→app/storage matching by token overlap. Pure, testable without a DB |
| `context.ts` | `formatGraphBlock(graph)` — serializes the graph into a compact block (~2000 chars) for the assistant's system prompt (priority: interests → routines → health → capabilities) + referenced `memoryIds` (for `touchMemory`) |

The graph is **per-user and 100% auto-derived**: nothing is persisted, no LLM call to build it (deterministic heuristics). Every assistant turn recomputes it.

### `agent/`

Conversational assistant. The engine is the **Vercel AI SDK v7** used as-is:
typed `streamText` + `tool()`, `toUIMessageStream`, and a single DB write
in `onEnd`. There is no more custom conversion between the DB, the LLM and the UI.

| File | Purpose |
|---|---|
| `threads.ts` | Threads and messages (`agent_threads`/`agent_messages`) — `ensureThread` (creates under the client-chosen id, refuses another user's id), `getThread`/`getThreadByContext`/`getOrCreateThreadForContext`, `listThreads`, `updateThreadTitle`, `deleteThread`, `loadMessages`/`saveMessages` (upsert of the full list), `appendMessage`, `messageText`. One row = one `UIMessage`, `parts` stored as JSON |
| `turn.ts` | One conversation turn: reloads history, assembles system prompt + tools + model, `streamText` with `stopWhen: stepCountIs(8)`, then `toUIMessageStream` whose `onEnd` rewrites the thread and triggers the post-turn step. `convertToModelMessages(..., { ignoreIncompleteToolCalls: true })` absorbs a previously interrupted turn |
| `tools.ts` | **Assistant surface** of the shared registry (`services/tools/registry.ts`) → typed `ToolSet`, + `buildAgentTools` (app manifest tools) and `destructiveToolNames` (list injected into the confirmation prompt). A failing tool **throws**: it's the SDK that produces the `tool-output-error` part. No tool is added here |
| `model.ts` | `getAgentModel` — the provider's model wrapped by `extractReasoningMiddleware({ tagName: "think" })`, for models that emit their reasoning inline |
| `prompt.ts` | `buildSystemPrompt` — role, rules, connected-service methods, user state block, scope block, language instruction |
| `scope.ts` | App / script / storage context: `resolveScope` (request + thread context) and `buildScopeBlock` (truncated HTML or code, storage keys, requested key's content) |
| `post-turn.ts` | Off the critical path, after persistence: `generateSuggestions` (follow-ups, called by its own route) + `runPostTurn` (memory extraction and thread title, best-effort) |
| `memory.ts` | Durable memory (`assistant_memory`) — `listMemory`/`addMemory`/`updateMemory`/`deleteMemory`, `formatMemoryBlock`, `touchMemory`, parsers and prompt builders (`buildExtractionPrompt`/`parseExtractionPayload`, `buildTitlePrompt`/`parseTitle`, `buildFollowupPrompt`/`parseFollowups`) |
| `overview.ts` | Aggregated overview (`getPlatformOverview`) — apps/scripts (health + last run), dashboards, connections, recent storages, memories, recent threads. One call for the assistant |
| `brief.ts` | Daily brief — `getOrCreateJournalThread` (thread with `contextKind: "journal"`, identified by its context rather than its title), `generateBrief` (overview + best-effort agenda/weather → `chatCompletion` → `appendMessage`), `shouldGenerateBriefForUser` + `runDueBriefs` |
| `own-tools.ts` | Assistant-specific tools (memory, overview, brief, state graph) declared in the shared registry — so also exposed via MCP |
| `schemas.ts` | zod schemas shared by the memory routes |

### `templates/`

| File | Purpose |
|---|---|
| `templates.ts` | `listTemplates`, `listTemplatesForUser(userId)` (adds `installed` via `apps.sourceTemplate`), `getTemplate`, `installTemplate(userId, slug)` — reads `templates/<slug>/{template.json, app.html}` from disk, `createApp` (with `sourceTemplate`) + `createVersion` + seed table storages |

### `dashboards/`

| File | Purpose |
|---|---|
| `dashboards.ts` | Dashboard CRUD, layout validation (`validateLayout`), `DashboardError`; 12-col grid, owner/visibility checks. Adds `addDashboardWidget` / `removeDashboardWidget` (auto placement) for the assistant |

Each service has a co-located `.test.ts`.

## Database (`src/db/schema.ts`, SQLite only)

Auth (better-auth): `user`, `session`, `account`, `verification`. The `admin`
plugin adds to `user`: `role` (`admin` | `user`), `banned`, `banReason`,
`banExpires`. RBAC: the first account created becomes admin (backfill migration
0006 + bootstrap hook in `lib/auth.ts`); policy in `lib/rbac.ts`; management
endpoints `/api/auth/admin/*` mounted by the plugin (admin-only).

Dashboards domain:
- `dashboards` — unique slug, name, ownerId, visibility (`private` | `family`), layout JSON (`{ cols:12, widgets: {i,appId,x,y,w,h,title?}[] }`), 12-col responsive grid, max 20 widgets

Assistant (`agent_*`, drizzle 0024):
- `agent_threads` — `id` (chosen by the client), `userId` → `user`, `title`, `contextKind` (`assistant`|`app`|`script`|`journal`, default `assistant`), `contextId` (appId/scriptId/userId), `createdAt`, `updatedAt` (index `agent_threads_user`, `agent_threads_context`)
- `agent_messages` — `id`, `threadId` → `agent_threads`, `role` (`user` | `assistant`), **`parts`** (JSON `UIMessage["parts"]`: text, reasoning, `tool-*`), `model`, `seq` (stable order within the thread), `createdAt` (index `agent_messages_thread`). One row = one `UIMessage`: the UI reads it back as-is and the LLM layer goes through `convertToModelMessages`, so there's no custom conversion on either side

Generation chat (apps/scripts), flat schema kept, fed by `src/services/messages/`:
- `assistant_threads` — `id`, `userId` → `user`, `title`, `contextKind` (`assistant`|`app`|`script`), `contextId`, `createdAt`, `updatedAt` (index `assistant_threads_context`)
- `assistant_messages` — `id`, `threadId`, `role` (`user` | `assistant` | `tool` | `plan`), `content`, `model`, `versionId`, `durationMs`, `createdAt` (index `assistant_messages_thread`)
- `assistant_memory` — `id`, `userId` → `user`, `kind` (`fact`|`preference`|`project`), `content`, `source` (`auto`|`assistant`|`user`), `threadId` (provenance → `agent_threads`), `pinned`, `useCount`, `lastUsedAt`, `createdAt`, `updatedAt` (index `assistant_memory_user`). Durable memory; source of the user state graph (`src/services/user-state/`), injected into the system prompt via `formatGraphBlock` (formerly `formatMemoryBlock`, capped at 2000 chars/40 items)

Apps domain:
- `apps` — slug, name, ownerId, visibility (`private` | `family`), hasUi, tags, currentVersionId, manifest (JSON of declared storages/tools, consumed by MCP/Assistant), sourceTemplate (slug of the source template if the app came from one)
- `app_versions` — HTML snapshots (html, prompt, model, manifest)
- `app_storage` — per-app JSON KV; **no `id` column**, composite key `(appId, key)`; `kind` kv/table + optional `schema` JSON
- `global_storage` — JSON KV shared across apps; composite key `(ownerId, key)`; `visibility` private/family (family = readable by everyone)

App manifest: `<script type="application/json" id="home-manifest">` in the generated HTML,
extracted by `extractManifestFromHtml` on every `codeApp`, validated by zod, stored on
`apps.manifest` + `app_versions.manifest`. Declarative mapping (`op`: get/set/list/append/remove/toggle/update
on a key) — never arbitrary JS. MCP and the Assistant expose these tools under the name
`app_<slug>__<tool>` (cap of 50 tools total). Prebuilt models live under `templates/<slug>/` (same HTML + manifest), installed via `installTemplate` — an installed app is a normal app (`apps.sourceTemplate` keeps track of the source template so already-installed templates can be hidden from a user's showcase; the `GET /api/templates` API returns an `installed` flag per user).

Messages domain (unified chat — legacy):
- `generation_messages` — old table (`user` | `assistant` | `plan`, `appId`/`scriptId`/`ownerId`) migrated to `assistant_threads`/`assistant_messages` (drizzle 0014 backfill). Kept temporarily read-only (fallback in `src/services/messages/chat.ts`) then removed in a future migration

Scripts domain:
- `scripts` — server scripts (formerly "crons"): no link to an app; `ownerId` + `visibility` (`private` | `family`) govern access; `triggerKind` (`schedule` | `manual` | `webhook`, default `schedule`); `schedule` 5-field (**empty** if unscheduled), `webhookSlug` (unique, if webhook) + `webhookSecret`, JS code (`async function main(home)`), enabled, nextRunAt/lastRunAt
- `script_storage` — per-standalone-script JSON KV; composite key `(scriptId, key)`; `kind` kv/table + `schema` (like `app_storage`, since drizzle 0019); used when the script has no app
- `script_runs` — history: status `success` | `error` | `timeout`, output, error, durationMs
- `script_run_spans` — execution trace as a tree (`parentId`): `step` (`home.step` groups), `call` (auto-traced `home.*` calls), `log` (console); indexed on `(runId, seq)`; retention: last 50 runs per script
- `script_versions` — code snapshots, restorable

Tracing lives in `src/services/scripts/traced-sdk.ts` (`createTracedHome`): it wraps
`buildScriptSdk` in a Proxy that records every SDK call + `home.step` pragmas.
The `// @step Label` comment pragma (implicit scope until the next `// @step` or end of run,
`// @endstep` optional) is transformed in `runner.ts` (`transformPragmas`) into
`home.__pushStep` — auto-popped at the next step / end of run.

Settings:
- `user_settings` — per-user provider/planner/coder/**assistantModel** overrides (+ locale) + **brief** `briefEnabled`/`briefHour`/`briefLastRunAt`
- `provider_keys` — one row per provider, encrypted API key (overrides env)

Programmatic access (REST + MCP):
- `api_tokens` — personal access tokens: `userId`, `name`, `tokenHash` (SHA-256, never plaintext), `prefix` (e.g. `hai_ab12cd34`), `createdAt`, `lastUsedAt`, `revokedAt` (soft revoke via `revokedAt IS NOT NULL`)
- `mcp_tool_calls` — MCP call history: `userId`, `toolName`, `tokenPrefix`, `args`/`result` (JSON truncated to 4 KB), `status` (`success`|`error`), `error`, `durationMs`, `createdAt` (index `user_created`, `user_tool`). Written best-effort from `services/mcp/server.ts` via `services/mcp/calls.ts`; exposed via `GET /api/mcp/calls` (scoped to `userId`, `limit` 1..100). Purged after 30 days / 500 rows max.

Connections:
- `connections` — type `google` | `smtp` | `imap` | `telegram` | `notion` | `homeassistant` | `weather` | `webhook`; `config` is an **encrypted blob** (AES-256-GCM); status active/error/expired

Migrations live in `drizzle/*.sql`; workflow: `npm run db:generate` then `npm run db:migrate`.

## Where `homeSDK` lives

Not a package — four coordinated pieces, **decoupled via the registry**:

1. **Bridge (iframe side)** — `BRIDGE` dynamically generated in `src/lib/app-runtime.ts` via `methodRegistry` (`buildBridgeEntries()` → `{ google{drive{list,read...}}, mail{send,search...}, telegram{send...}, notion{...}, homeassistant{...}, weather{...}, webhook{...} }` + `storage` (with `storage.global.*`), `http`, `ai` outside the registry). Exposes `window.homeSDK`.
2. **Relay (parent side)** — `src/components/AppFrame.tsx` listens for `postMessage` type `"homesdk"` and POSTs to `/api/apps/[id]/rpc` (with an `e.source` check for multi-iframe dashboards)
3. **Server dispatcher** — `bridgeRpc.handle()` in `src/lib/app-runtime.ts`: `storage.*`/`storage.global.*` resolved via a `StorageScope` (single branch), `ai`/`http.fetch` hardcoded, otherwise looked up via `getMethod(method)` → `getProvider(type)` → `provider.sdk.methods[methodKey](cfg, ...args)`
4. **Script twin** — `buildScriptSdk(ownerId, {scriptId, runId, webhookPayload})` in `src/services/scripts/sdk.ts`: same dynamic generation from `connectionRegistry` (looping over `provider.sdk.methods`, shared `mail` handling). `home.storage.*` is on `scriptScope`; `home.app(appId).storage.*` is on `appScope`, with a `getApp(ownerId, appId)` check on every call. No more switch or per-store branch. `home.webhook.payload` exposes the body of an incoming webhook (null otherwise).

Adding a connection = creating `src/services/connections/<type>.ts` that exports `<type>Provider` (zod `schema` + `test` + `sdk`), then 1 line in `registry.ts`. The LLM prompt (`getSdkPromptLines()`) and `POST /api/connections` adapt on their own — no need to touch `app-runtime`, `sdk`, or `generation`.

## Programmatic access (external agents: REST + MCP)

An external agent (e.g. hermes on a VPS) talks to home-ai without a browser
session, via a **personal access token**:

- Mint one in the Settings UI → "Personal access tokens" or `POST /api/tokens`
  (the `hai_...` token is shown once). Revoke: `DELETE /api/tokens/[id]`.
- Send it as `Authorization: Bearer hai_...` on any `/api/*` route.
  `requireUser()` (src/lib/session.ts) resolves either the session cookie or the
  Bearer token — a single guard for everything. The token is stored as a SHA-256 fingerprint.

**MCP endpoint**: `POST /api/mcp` (Streamable HTTP, **stateless** mode). It
reuses the existing services and the same auth guard. Tools come from the **shared registry** (`src/services/tools/registry.ts`): `buildMcpServer(userId, {tokenPrefix})` loops over it and no longer defines any tools itself. MCP therefore exposes the same 42 tools as the assistant, plus the tools declared by apps (`app_<slug>__<tool>`, via `registerManifestTools`).
Every tool checks ownership (via `getApp` / `getScriptWithApp`) before acting. Every call is traced best-effort into `mcp_tool_calls` (`services/mcp/calls.ts`: `logMcpCall`/`listMcpCalls`) with `durationMs` + `tokenPrefix` (`hai_…` prefix). Diagnostics: `GET /api/mcp/tools` (catalog serialized for the UI) + `GET /api/mcp/calls` (history) + `Settings → MCP` page (`settings/mcp`: URL, hermes/Claude snippets, filterable catalog, recent activity).

**Global assistant**: `assistant` page + `assistant` API:
- UI `src/app/assistant/[[...threadId]]` (full-screen catch-all). The **server page** loads the thread and the conversation list and passes them as props: no client-side history fetch, no loading state. `AssistantPageClient` + `agent/ThreadSidebar` (presentational, refreshed via `router.refresh()`) + `agent/ChatView` (`useChat` + `DefaultChatTransport`, rendered per part type, reasoning/tool collapsed by default, editable `PlanCardPart`). `agent/Overlay.tsx` drawer (⌘J, app/script/storage scope without navigation) + Settings → Memory / Brief
- **The thread id is chosen by the client** and sent back on every turn; `ensureThread` creates it on demand. Nothing needs to come back from the server during the stream (no more `data-thread`), and resuming a thread is idempotent
- API `POST /api/assistant/chat` (`{ id, message, scope?, locale }` — only the last message is sent, the server holds the history; capped at 32k characters), `GET /api/assistant/threads` (+ `?contextKind=&contextId=` filter), `GET /api/assistant/threads/[id]` (→ `messages: UIMessage[]`), `DELETE /api/assistant/threads/[id]`, `POST /api/assistant/suggestions` (follow-ups, outside the stream so they don't delay its closing), `GET/POST /api/assistant/memory` + `PATCH/DELETE /api/assistant/memory/[id]`, `GET /api/assistant/overview`, `POST/GET /api/assistant/brief`, `PUT /api/settings` (assistantModel + brief*)
- Engine: typed `streamText` + `tool()` + `toUIMessageStream`, `stopWhen: stepCountIs(8)`. Persistence happens **exactly once**, in `onEnd`, by rewriting the list the SDK produced. Same `requireUser()` guard as REST/MCP. Effective model: `assistantModel` → env `LLM_ASSISTANT_MODEL` → `LLM_PLANNER_MODEL`. Brief via `runDueBriefs` in `instrumentation.ts`

Connecting hermes:
```sh
hermes mcp connect https://<domain>/api/mcp --header "Authorization: Bearer hai_..."
```

## Conventions to know

- Code comments and UI strings are **French**.
- API routes are thin: parse input, call a service, return JSON via `apiError(err)` on failure.
- Tests are vitest, co-located next to the file they test.
